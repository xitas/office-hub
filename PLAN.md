## Overview

An office CRM for small-to-mid-sized offices (10–100 staff). It works on desktop with a left sidebar and is fully responsive on mobile with a bottom nav.

**Stack**

| Layer | Choice |
|---|---|
| Backend | Django 5, Django REST Framework, SimpleJWT, django-filter, drf-spectacular |
| Real-time | Django Channels + Daphne (in-memory layer in dev, Redis in prod) |
| Database | PostgreSQL 16+ |
| Frontend | React + TypeScript (Vite), Tailwind CSS v4, shadcn/ui, React Router, TanStack Query |
| i18n | react-i18next — English and Urdu (RTL) |
| 2FA | TOTP (pyotp) with hashed backup codes |

**Key architecture decisions**

- Custom `User` model with email login and a `role` (admin / manager / staff) and `department`.
- **Permissions:** a single permission matrix (`apps/core/permissions.py`) covers every module. `ModulePermission` enforces it on each viewset, and `ScopedQuerysetMixin` limits rows (staff → own, manager → department, admin → all).
- **Audit log:** `AuditedViewSetMixin` records who changed what and when, including a field diff, on every create, update and delete.
- **Notifications:** `notify()` respects each user's preferences. It sends in-app notifications live over WebSocket and also sends email.
- **Global search** and **dashboard** use registries, so each new module plugs in without changing the API contract.
- **REST API:** everything is under `/api/v1/` with JWT auth and OpenAPI docs at `/api/docs/`, so a mobile app can be added later.

**Prerequisites:** Python 3.13, Node 22+, PostgreSQL 16+. Redis is needed in production only. See `README.md` for setup.

Declining location still allows check-in, marked "no location". Location needs HTTPS (localhost in development); `Permissions-Policy` already allows `geolocation=(self)`.

## Known limitations (all phases)

Collected from the phase sections (which keep their own notes and dates).

**Accounts, roles and the app (Phases 1–2)**
- Three roles (admin, manager, staff) and one department per person; managers see their own department. No projects yet: "By project" filters, project channels and linking tasks to projects wait for them.
- Emails are plain text; Urdu reads right to left only where the email app detects it (HTML emails with `dir="rtl"` would be better). No mobile push notifications: in-app (live over WebSocket) and email only.
- Text people type (names, units, goal names, tags) shows as typed in both languages unless an Urdu name field exists.
- Task status-change notifications aren't sent (assigned, due soon, overdue, comments and @mentions are). The task calendar returns up to 1,000 tasks and the board 100 cards per column (fixed queries, but 0.4–0.9 s to serialize at that size). A contact's or company's activity loads every linked task event without paging.

**Communication (Phase 3)**
- No group direct messages, project channels or threads (replies quote). Presence comes from open WebSocket connections (75 s without a ping is offline).
- Communication log types are call, meeting, email, WhatsApp and note (no separate SMS). Templates have no invoice placeholders. Announcements publish at once, go to everyone or whole departments, and an edit doesn't notify again.

**Office planning (Phase 4)**
- Bookings repeat weekly only; meetings don't repeat; no sync with outside calendars.
- One set of office hours and one working week for everyone (no shifts, part-time patterns or overtime). Office check-in is self-reported. Check-ins on days off and office holidays are never late (since Phase 6).
- Leave allowances are yearly and set by admins (no monthly accrual; carry-over by hand); a half day covers one day. Expenses are in the office currency only, "paid" is a record (no payroll or accounting export). Weekly goals are numbers entered by hand, not linked to tasks.

**Local coordination (Phase 5)**
- Location only at visit check-in and check-out (never tracked), as accurate as the phone says, over HTTPS only; exact coordinates are removed after 90 days.
- OpenStreetMap's public tiles: fine for an office this size; heavy or public use needs a tile provider or our own cache. No offline maps. Address search only centres the map.
- Photos are JPEG, PNG or WebP (HEIC needs the browser to convert it). Errands have one runner, no money handling, no repeats or route planning; vendors have no price lists.

**Reports (Phase 6)**
- Worked out live for at most a year; no snapshots, scheduled or emailed reports, or period comparisons. PDFs are tables only, and their Urdu text doesn't copy cleanly (the Excel files carry the real text). Attendance counts from the account's creation (no employment start dates).

**Running it**
- Reminders, digests, overdue notices and location removal need Celery Beat and a worker running (every minute to daily, see each phase). Dev runs the channel layer in memory, so `notify()` from a shell or worker needs `REDIS_URL`.
- Files are stored on the local disk (`MEDIA_ROOT`, and `PRIVATE_MEDIA_ROOT` for attachments, photos and receipts); S3-compatible storage is possible later via `STORAGES`.
- Dependency follow-ups: the Twisted advisory exception, the audit reading `requirements.txt` instead of the lock (Pillow and certifi pins to raise), and the dev-only `shadcn` CLI's npm advisories (see Open questions).

## Next: deployment

Nothing here is decided yet. To settle before going live:
1. **Hosting:** where the backend (Daphne for HTTP and WebSockets, a Celery worker and Celery Beat), PostgreSQL 16+, Redis and the built frontend run; one server or managed services; how the processes are kept running and restarted; HTTPS certificates (location and secure cookies need HTTPS).
2. **Domain:** the address staff use, and whether the API is on the same origin (simplest: the frontend host proxies `/api`, `/ws` and `/media`) or a subdomain (then CORS and CSRF origins, and `connect-src` in the CSP, must name it).
3. **Email provider:** an SMTP or API provider for notifications, digests and password resets (`EMAIL_URL`, `DEFAULT_FROM_EMAIL`), with SPF, DKIM and DMARC set up on the domain.
4. **Backups:** scheduled, off-site and tested backups of the PostgreSQL database and of `private_media` (attachments, visit and errand photos, receipts) and `media` (avatars), with how long they're kept and a practised restore; `FIELD_ENCRYPTION_KEYS` must be backed up separately (encrypted fields can't be read without them).
5. **Content-Security-Policy for the frontend host:** the README's policy (`img-src` with `https://tile.openstreetmap.org` for the map, `blob:` for thumbnails, `connect-src 'self' wss:`), plus `Referrer-Policy: strict-origin-when-cross-origin` (the tile policy forbids `no-referrer`) and the same `Permissions-Policy` (`geolocation=(self)`). The backend's own CSP is set in `config/settings/prod.py`.
6. **Nominatim:** `NOMINATIM_CONTACT_EMAIL` (a monitored address for the office or its IT contact) and `NOMINATIM_COUNTRY_CODES` (default `pk`); with many offices or heavy use, a paid geocoder or our own Nominatim.
7. **Production `.env`:** `DJANGO_SECRET_KEY` (new, random), `DJANGO_DEBUG=False`, `DJANGO_ALLOWED_HOSTS`, `DATABASE_URL`, `REDIS_URL`, `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS`, `FRONTEND_URL` (links in emails), `FIELD_ENCRYPTION_KEYS` (new; the app won't start without them), `EMAIL_URL`, `DEFAULT_FROM_EMAIL`, `NUM_PROXIES` (behind a proxy), `LOGIN_THROTTLE_RATE` and `CHAT_SEND_RATE` (defaults are fine), the `SECURE_*` HSTS settings (preload only once the domain is ready), `API_DOCS_ENABLED` (off by default). Check with `python manage.py check --deploy --settings=config.settings.prod`.
8. **Before the first deploy:** raise the Pillow and certifi pins and point the audit at the lock (see Open questions); run `migrate`, create the first admin (not `seed_demo`), set the Organization settings (name, time zone, week start, working days, office hours), leave types and departments.
